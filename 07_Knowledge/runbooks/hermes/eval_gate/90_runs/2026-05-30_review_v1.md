## 1. Docstring 風格

### 保留／修改

| 元素 | 裁決 | 理由 |
|------|------|------|
| 規則函數 docstring 模板（觸發條件→依賴欄位→意圖） | **保留** | 一致性高，與現有 `evaluate_task_record` Google-style 匹配 |
| Helper 函數 docstring（`_int_field`、`_float_field`） | **保留**，但未來可簡化 | 純取值工具，3–5 行即可（見下方「不喜歡的點」） |
| `_RULES` 區塊註解 | **保留** | 清楚、含新增規則指引 |
| 跨引用 DEBT_LOG（D-004、D-005） | **保留** | 有助 maintainer 了解關聯 issue |
| `# ── 五條核心規則 ──` 區塊分隔 | **保留**，但可刪減重疊描述 | 下層各函數 docstring 已含對應資訊 |

### 我喜歡的點

1. **模板一致性**：所有 `_rule_*` 使用相同三段結構（觸發條件 / 依賴欄位 / 意圖），降低認知負擔。
2. **Google-style 格式**：與既有的 `evaluate_task_record` docstring 格式一致，無混用風險。
3. **設計決策記錄到位**：
   - `_float_field(default=1.0)` 的「樂觀預設」語意在 docstring 中寫明。
   - `_total_context_tokens` 標記了「與 eval_exporter 重複」（D-005）。
   - `_rule_context_heavy` 記錄了 `>` vs `>=` 不一致（D-004）。
4. **例外路徑有說明**：`_collect_schema_issues` 的 Returns 包含缺失/型別錯誤的範例字串。

### 我不喜歡的點

1. **Helper docstring 過長**：`_int_field`（18 行 docstring）和 `_float_field`（24 行）對純取值工具來說 verbosity 偏高 — 3–5 行即可（功能描述 + 預設值說明）。
2. **區塊註解與函數 docstring 重疊**：`# ── 五條核心規則 ──` 底下的段落（簽章統一、回傳格式）其實可以併入 `_RULES` 註解或第一條規則 docstring，不必在區塊級重複。
3. **`_collect_schema_issues` 的非必要擴充**：原本一行 docstring 就夠了，擴充成三段式雖然無害但略顯囉嗦。

### 下次規則

1. **工具函數 docstring 長度建議**：純取值/轉換的 private helper → 單行或 3 行 max（功能描述 + 1 個 Args + 1 個 Returns）。規則函數 → 允許 8–15 行（觸發條件 + 依賴欄位 + 意圖）。
2. **區塊註解不重複 docstring**：`# ──` 區塊分隔只放導覽性標題，不重複下層函數已經說明的內容。
3. **跨引用 DEBT_LOG 保持**：當 docstring 提及已知 issue 時，附上 `（見 DEBT_LOG D-XXX）` 是好的慣例，繼續保持。

## 2. Logging 風格

### 保留／修改

| 項目 | 裁決 | 理由 |
|------|------|------|
| 5 條 log 呼叫總量 | **保留** | 符合 §9.4「不超過 3 條 INFO」上限 |
| 等級分配（2 INFO + 2 WARNING + 1 INFO） | **保留** | 合理：WARNING 留給 schema 問題 |
| `%s` 延遲格式化 | **保留** | 正確做法 |
| 不記錄整個 record dict | **保留** | 避免敏感資料洩漏 |
| D-006 靜默 fallback DEBUG log | **未納入**（scope 外） | 留待 Week 3 或 D-006 專門修正時補上 |

### 我喜歡的點

1. **數量克制**：不多不少，只在「進入點 / schema 失敗 / 規則結果摘要」三處決策點記錄，沒有在每條規則內爆 log。
2. **等級合理**：WARNING 保留給「上游資料結構異常」，INFO 保留給正常決策路徑，分工清楚。
3. **`%s` 延遲格式化**：遵循 §9.3 規範，不浪費 CPU。
4. **區分 passed vs tags fired**：兩條不同的 INFO log，讓下游 dashboard 可以直接過濾「通過率 vs 觸發率」。

### 我不喜歡的點

1. **`_total_context_tokens` 回傳 0 無日誌**：回傳 0 有兩種可能（a）上游無 `context_token_usage` 欄位（b）有欄位但值為 0。目前無法區分。但本輪刻意不加入 DEBUG log（見 §9.4「helper 內部不記錄」），建議另開輕量條目。
2. **規則迴圈外無 ERROR log**：如果某個 `_rule_*` 拋出例外，目前沒有任何 ERROR log（D-007 範圍）。這在 Week 3 補上 try/except 時自然解決，但本輪至少應在 DEBT_LOG 中標記「缺乏 ERROR level log coverage」。

### 下次規則

1. **ERROR 等級應保留給 try/except 邊界**：當規則函數拋出非預期例外時，使用 `logger.error` 記錄規則名稱與例外訊息。
2. **靜默 fallback 可考慮 DEBUG 等級**：對於 D-006 的嵌套欄位缺失，若未來加入 DEBUG log，需確認不會造成 log 洪水（記錄頻率 = 每條缺失的 task record × 每輪掃描次數）。
